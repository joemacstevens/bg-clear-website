## What happened

Joe came in with "get acclimated" — no implementation task. I oriented against AGENTS.md, the journal, and git log, then he steered into a scoping conversation: "How is this site connected to WooCommerce and Bank of America?" My honest answer was "it isn't — there's no Woo client, no payment SDK, and the only payment surface is a manual `payment_collected` status flip." That kicked off the actual work.

We landed on:
- **WooCommerce as a fulfillment sink** — Supabase stays the catalog source of truth, approved orders push into Woo one-shot, ad-hoc line items (no Woo product matching)
- **Bank of America via Cybersource Secure Acceptance Hosted Checkout** — customer self-serve invoice pay, full redirect, SAQ-A scope, no card data ever touches our servers

Plan written, reviewed by a Plan agent, approved, then I built it. New code:
- Migration `20260411000012_add_woo_and_payments.sql` — adds Woo sync columns to `orders`, creates `payments` table with the RLS pattern that matches the project's `current_setting('request.jwt.claims')` convention (the one that doesn't trigger the infinite-recursion bugs we've hit twice before)
- `src/lib/server/integrations/woo.ts` — `pushOrderToWoo()` with row-claim idempotency, 3-second `AbortController` timeout, ad-hoc line items carrying `bg_product_id`/`bg_sku`/`vendor_name` in `meta_data`, never throws
- `src/lib/server/integrations/cybersource.ts` — `buildSignedPaymentRequest()` and `verifyResponseSignature()` using HMAC-SHA256 with `crypto.timingSafeEqual` for constant-time compare
- Hooks: admin approve action and rep order-create (non-approval branch only) now fire the Woo push
- New admin page `admin/orders/[orderId]` — view detail, see Woo sync status/attempts/error, retry button when failed, payments table
- Customer-side: "Pay Invoice" CTA on `catalog/orders/[orderId]` when status is past approval and not paid; new auto-submitting form route at `catalog/orders/[orderId]/pay/`; new result page at `catalog/orders/[orderId]/payment-result/` with polling fallback so the browser-redirect race against the S2S callback doesn't leave the user staring at a stale page

- Amount tamper guard: compare `req_amount` cents to the order's recorded subtotal before persisting
- `.env.example` updated with eight new vars and inline comments about how to configure the Cybersource profile

## Decisions

- **Guest checkout in Woo, not Woo customers.** No `findOrCreateWooCustomer` in v1, no `woo_customer_id` on profiles. Flagged for Evans to confirm before launch — it's the easiest thing to flip later if ops wants customer records.
- **Both browser-return and S2S callbacks supported, S2S is authoritative.** UNIQUE constraint on `cybersource_transaction_id` means whichever arrives first wins; the other one short-circuits as a duplicate. No race, no double-charge state.
- **Capital 50/50 split punted to v2.** Evans' schedule has deposit/final payment terms for capital equipment; we're shipping single-payment-per-order first and handling capital manually.
- **Pay trigger is customer self-serve only.** No rep-emailed payment link in v1. Pushed back when I considered the email path — it would need Resend/Postmark + signed-URL infra, and the value vs. portal-CTA is marginal.
- **`payment_collected` boolean stays as the convenience flag**, but the source of truth shifts to `EXISTS payments WHERE decision='ACCEPT'`. The webhook updates both atomically so existing code that reads the flag keeps working.

## Problems/Bugs

- **svelte-check went from 341 errors to 467 in this branch.** Every new one is the same `Property 'foo' does not exist on type 'never'` pattern that already plagues `rep/pricing`, `rep/quotes`, and every other server-side file in the repo. The project's hand-rolled `Database` type is skeletal — supabase-js infers `never` for the row types. Functionally fine, ships fine on Vercel, but it's lying technical debt that bites every PR review. Worth a separate task to either auto-generate the Database type from the live schema or stub out the relationship types.
- **`npm run build` fails locally** with `"PUBLIC_SUPABASE_URL" is not exported by " virtual:env/static/public"`. I checked: same failure on main with no `.env` present. Vercel's build has env vars set; this is a local-only issue.
- **Cybersource signing not yet verified against the live test endpoint.** I implemented the Secure Acceptance signing spec by the book (signed_field_names is itself signed, `,`-joined `name=value` input, HMAC-SHA256 → base64), used `crypto.timingSafeEqual` for verification, and the unit tests in the plan's verification section will catch any signing mistake immediately. But until we run an actual test transaction against `testsecureacceptance.cybersource.com`, the signing isn't proven correct against the real implementation.
- **No automated test coverage.** The repo has no test runner. All verification is manual per the plan's e2e steps. Should add a vitest setup for the integration modules at least — pure functions like the signing helpers and the amount-cents parsing are perfect targets.
