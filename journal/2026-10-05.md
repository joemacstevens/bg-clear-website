# 2026-10-05 — Invoice payments: the outage, the webhook, and the code that wasn't in GitHub

## What happened

A customer tried to pay INV-24967459 ($1,300) on the public Pay-an-Invoice page
and got "The payment system is temporarily unavailable." Joe had cancelled
Pressable on Sep 11 (nobody seemed to be using it), which deleted the WordPress
site that runs WooCommerce + Bank of America's CyberSource plugin. Joe
reactivated it and Pressable restored the site from backup at the same URL.
Joe came in with a brief from an earlier cloud session: find the code, check the
restored site, figure out why no invoice has ever been marked paid, run a $1
test, get it all into GitHub.

## The conversation / what I found

**The code was never lost, just never pushed.** The main checkout is sitting on
`feature/ecommerce-quote-to-payment` with 8 local commits (Jun 30 – Jul 9) that
never reached GitHub: email notifications, the rep "Pay Links" page, the public
`/pay-invoice` page, the webhook's manual-invoice branch, and the
`manual_invoices` migration. Production was deployed straight from that local
branch with the Vercel CLI (prod = `c962f25`), so the live site ran code
GitHub had never seen.

The brief said seven migrations were missing from the repo. Six of them were
actually on GitHub already, just on the feature branch, never merged to main.
Only `manual_invoices` was truly local-only. But the filenames didn't match the
versions the DB recorded (files were hand-numbered `…000001`, the MCP applies
recorded real timestamps), and two files shared `20260608000001`. I pulled the
applied SQL out of `supabase_migrations.schema_migrations` and diffed it: same
statements, minus comments. `browse_categories` on disk is a superset (extra
subcategories + product mapping), and the DB has that data, so it was run
separately. Renamed all seven files to the DB versions.

**Today's failure** was the site being gone. `createWooOrder` threw, the action
deleted the just-inserted row (hence "no row in Supabase") and returned the
generic 502. The real error was swallowed by a bare `catch {}`, so Vercel logs
show one 502 on `/pay-invoice` and nothing else. After the restore, the Woo API
answers with the existing keys, and the order-pay page renders the CyberSource
card form.

**Why nothing ever got marked paid. Two separate reasons, and the first one is the big one:**

1. **No payment has ever completed in WooCommerce.** All 21 Woo orders, including
   the four real invoices (#38–#41: $850, $1,884.88, $3,073.19, $563.50), are
   still `pending`, with zero order notes and no transaction IDs. The webhook
   never had a paid event to send. That fits the open item in memory from Jun 7:
   the CyberSource plugin threw `RESOURCE_NOTFOUND` on the pay page and nobody
   ever saw a card clear. So those four customers either paid some other way or
   haven't paid. Someone needs to check with BoA/accounting.
2. **The webhook was dead anyway.** Woo webhook #1 was `disabled`, pointing at
   `https://bg-clear-website.vercel.app/api/woocommerce/webhook`, which 404s
   (the route is `/api/webhooks/woocommerce`). Woo auto-disabled it after
   repeated failures (last modified Jun 30). Also: apex `bgclear.com`
   308-redirects to `www`, so the URL must use `www`.

I proved the prod webhook secret matches the local one without printing it, by
signing a no-op `status: pending` payload and POSTing it to prod (200
`ignored: pending`, vs 401 for a bad signature).

## Then the form itself turned out to be broken

Joe tried the $1 test and hit "Enter your invoice number." on every submit, with
the form wiped. curl POSTs to prod worked fine, so I reproduced it in the browser
pane with a `formdata` listener. The inputs held the typed values when `submit`
fired, but the entry list the browser built was all empty strings. The culprit is
`onsubmit={() => (submitting = true)}`: flipping that state reran the one-way
`value={form?.values?.x ?? ''}` attribute effects, which wrote `''` back into
every input before the browser serialized the form. Fix: `bind:value` to local
`$state` seeded from `form.values`. Confirmed both ways on localhost: old file
gives an empty POST, the new one sends everything and keeps the values after a
server error. (Used an `a@b` email so the server rejects it before Woo, so no orders.)

So the public self-serve page has likely never worked for a real person typing
into a hydrated page. All four real invoices came from rep-generated links, not
this form. Today's customer's 502 must have slipped through somehow (e.g. a submit
before hydration), which is also why it reached Woo at all.

## The $1 test worked, first real payment ever

After deploying the form fix to prod (`vercel deploy --prod` from a clean
`git archive` of the branch, so nothing untracked got uploaded), Joe paid $1 on
the live page as TEST-1005. The whole chain worked on the first try:
- `/pay-invoice` created the `manual_invoices` row and Woo order #42.
- CyberSource: "Charge Approved: MasterCard" + "authorized by Bank of America
  fraud management". So the June `RESOURCE_NOTFOUND` problem is gone (probably
  fixed in the plugin settings at some point, or by the restore).
- Woo moved #42 straight to `completed` (fee-only order, nothing to ship). That's
  in PAID_STATUSES, good.
- Webhook delivered at 18:29:14. Vercel log: `[woo-webhook] woo #42 completed →
  manual invoice TEST-1005`. Row flipped to `paid` with `paid_at` 1s after Woo's
  `date_paid`.

This is the first card ever charged through this stack.

## Decisions

- Tried to PUT the Woo webhook (active + `www.bgclear.com/api/webhooks/woocommerce`
  + secret). **The auto-mode classifier blocked it.** Fair enough: it's a live
  integration change. Joe said "retry the webhook update via the API", and it
  went through: webhook #1 is now `active` at the `www` URL with the matching
  secret (confirmed by reading it back).
- Didn't touch the CyberSource plugin settings (Joe's rule). Read-only check:
  enabled, `environment=production`, `transaction_type=charge` (so success →
  `processing`, which the webhook treats as paid), all credential fields set,
  debug off, Decision Manager on (a review hold would land in `on-hold`, which
  we deliberately don't count as paid).
- PR targets `feature/ecommerce-quote-to-payment`, not `main`. Main is 41 commits
  behind and conflicts in 10 files (it still has the abandoned direct-CyberSource
  approach from PR #25 plus the branding pass, neither of which is in prod).
  Reconciling main is a separate product decision.

## Built

- `/pay-invoice` and `/rep/invoices`: `console.error` the real Woo failure.
- Webhook manual-invoice branch: logs which invoice flipped (or "no pending row
  matched"), returns `updated` count; setup comment names the exact URL.
- `.env.example`: the four `WOOCOMMERCE_*` vars as placeholders.
- Verified locally: build passes; signed no-op webhook calls hit the new log
  line and touched no rows.

## Problems/Bugs

- Vercel MCP can't list env vars (403), and runtime log text search times out

- Invoice numbers typed by reps have stray spaces ("INV -24967451"). Cosmetic,
  but it'll bite reconciliation. Not fixed.
- Test junk still in Woo + `manual_invoices` (#31–#37 and their rows).
