# 2026-06-30 — Filling in the email notification gaps

## What happened

Resend went live in prod yesterday (domain verified, API key set by Joe, `customercare@bgclear.com` as the from). Today Joe said it looked like it was working "but I think we need a few more email notification points" and asked me to review where transactional touchpoints made sense. I came back with a list of seven gaps across the quote→order→payment→fulfillment lifecycle. His reply: "Do them all."

So I did all of them.

## The work

Added seven new templates to `src/lib/server/email.ts` (plus a little `money()` helper so totals format consistently), then wired each one into the action/handler that actually represents the moment it should fire:

- **Approval needed** — rep submits a below-target quote → admin inbox (`submitForApproval`).
- **Quote rejected** — admin bounces the pricing → assigned rep, with the rejection notes (`admin/quote-approvals` reject).
- **Order confirmation** — fires from BOTH the rep in-person close (`rep/quotes/[id]` createOrder) and the customer accept (`catalog/quotes/[id]` accept).
- **Order placed** — customer accepts → rep gets the heads-up.
- **Payment receipt + order paid** — the Woo paid webhook now emails the customer a receipt and pings the rep + internal inbox.
- **Order shipped** — rep flips status to `shipped` → customer gets it with tracking number if present.

## Decisions / things I had to get right

- **Idempotency on the payment emails.** The Woo webhook already used `.eq('payment_collected', false)` as an idempotency guard. I added `.select(...)` to that same update so it returns the row ONLY on the first paid event — that's what gates the emails. A duplicate webhook updates zero rows → no second receipt. Felt clean to reuse the existing guard rather than invent a new one.
- **Everything fire-and-forget.** Every send is in a try/catch that only logs. An order or a webhook 200 must never hang or fail because Resend had a bad minute.
- **FK hint for the rep on rejections.** Had to grab the rep via `profiles!quote_requests_assigned_rep_id_fkey` — double-checked the constraint name was already used over in `rep/quotes/+page.server.ts` before trusting it.
